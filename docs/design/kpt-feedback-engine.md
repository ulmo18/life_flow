# KPT 회고 피드백 시스템: 현황 분석과 기술설계

초기 분석 기준: 2026-10-31 작업 트리의 코드와 문서. 아래는 기본적으로 설계이며, 실제 적용된 범위는 다음 구현 현황 업데이트를 기준으로 한다.

최신 제품 결정: Try와 실제 일정의 연결 기능은 당분간 비활성화하며 기존 관계 데이터는 보존한다. 자동 발행 설정과 실행 경로는 제거한다. 발행 회고와 일정 미리보기는 같은 신문 본문을 사용한다.

화면 개선: 발행된 날은 신문 링크를 먼저 보여주고 편집 가능한 날짜에는 별도의 수정 화면에서 현재 기록을 읽는다. 발행 신문과 일정 미리보기의 계획·실제 비교와 일정 목록을 하나로 통합했다. 일정 기반 피드백은 숫자를 반복하는 대신 기록에서 이어가거나 바꾸고 싶은 선택을 묻고, 루틴 이정표·기간 변화는 근거를 유지한다. 질문은 사용자가 직접 판단하도록 돕는 선택적 안내이며 행동의 성공이나 원인을 추정하지 않는다.

제품 결정: 과거 발행 회고도 저장된 기록 스냅샷에 항상 현재 피드백 규칙을 적용한다. 발행 당시 문구나 규칙 버전은 고정 저장하지 않으며, 규칙이 바뀌면 과거 회고의 문구도 바뀔 수 있다. 근거 보기에 이 기준을 표시한다. 재발행은 기록 스냅샷을 갱신한다. 기존 Try 후속 연결은 별도의 현재 관계로 유지한다.

이전 구현 기록 (C01, 현재 비활성): Try 연결 영역에서 사용 가능한 직접 연결 건수를 표시했다. 현재 화면과 변경 경로는 제공하지 않는다.

이전 구현 기록 (Try 명시 연결, 현재 비활성): 사용자가 Try 전체와 이후 실제 일정을 연결·해제할 수 있었다. 기존 관계 및 연결 당시 원문은 삭제하지 않는다.

구현 현황 업데이트 (D05): 새로 발행하거나 재발행할 때 동일 루틴의 시작일과 회고일까지의 완료 날짜를 버전 2 스냅샷으로 저장한다. 회고일을 포함한 최근 7일과 그 전 7일이 모두 루틴 기간에 포함되고 각각 3일 이상 완료되었으며 횟수가 다를 때, 기록된 날짜 수의 차이를 표시한다. 근거 보기에는 비교 기간과 완료 날짜를 표시한다. 루틴 60일 이정표와 직접 연결 계획이 우선하며, 근거가 불완전한 구버전 스냅샷은 비교하지 않는다. 원인이나 성격을 추정하지 않는다. 기존 열을 재사용하며 과거 데이터는 소급 변경하지 않는다.

구현 현황 업데이트 (D01): 우선할 직접 연결 계획이나 루틴 이정표가 없으면 발행된 실제 일정의 건수와 기록 시간 합을 표시한다. 시간이 겹치면 건수만 표시하며, 실제 일정의 원본 ID 누락·중복이나 시간 오류는 기존처럼 피드백 생략으로 처리한다. 계획 없는 날을 실패로 해석하지 않는다.

구현 현황 업데이트 (D03 확장): A·B·C·D 중요도별 직접 연결 실제 기록의 건수와 시간 합을 지원한다. 여러 중요도의 기록이 있으면 A→B→C→D 순으로 한 가지만 선택하고 각각의 기록을 섞지 않는다. 블록과 항목 ID가 맞는 고유 실제 기록만 포함하고 미연결 기록은 분류하지 않는다. 해당 실제 기록들이 겹치면 시간 합을 표시하지 않고 연결 건수만 보여 준다. 루틴 이정표가 우선이며 발행 스냅샷 외에 새 저장은 없다.

구현 현황 업데이트 (D02): 선택된 중요도의 직접 연결 계획 블록이 한 개인 경우, 근거 보기에서 계획 시간과 연결된 실제 일정 시간의 합을 비교한다. 중복 블록 ID, 시간 미정, 잘못된 시간, 연결된 실제 일정 간 겹침은 비교 대상에서 제외한다. 시간 차이를 실패·미수행으로 해석하지 않는다. 기존 스냅샷을 이용하므로 DB 변경은 없다.

구현 현황 업데이트 (A2): 같은 루틴의 완료 날짜가 회고일을 포함해 누적 정확히 60일인 경우, 연속 여부와 관계없이 60일 기록을 피드백 한 건으로 우선 표시한다. 초기 스냅샷은 최대 61개, 버전 2 스냅샷은 회고일까지의 완료 날짜를 저장하며 화면에는 최근 다섯 날짜와 나머지 일수를 근거로 표시한다. 61일 이상이거나 마지막 완료일이 회고일이 아니면 이 규칙을 표시하지 않는다. 발행 후 원본 변경은 기존 스냅샷을 바꾸지 않으며 재발행하면 다시 수집한다. 기존 스냅샷은 소급 추정하지 않는다. 알림, 습관 형성 판단 및 전체 고도화 범위는 구현하지 않았다.

구현 현황 업데이트: A1의 첫 규칙을 적용했다. `RetrospectFeedbackService`는 발행 스냅샷만으로 직접 연결된 B 계획의 블록 수·실제 건수를 우선 제시하고, 해당 조건이 없으면 실제 일정 건수를 제시한다. 신문형 회고의 KPT 아래에서 최대 한 문장과 접힌 근거를 보여주며, 근거의 원본 ID 부재·중복이나 시간 오류가 있으면 생략한다. 두 규칙은 기록의 횟수를 알려줄 뿐 KPT 의미, 미수행, 성격이나 성공을 추정하지 않는다. KPT 원문·DB는 변경하지 않고 분석 결과를 별도로 저장하지 않는다. 발행 재시도·재발행 후에는 현재 저장된 스냅샷으로 다시 계산되며, 발행 당시 규칙의 버전 보존과 새 알림의 중복 제어는 아직 구현하지 않았다. 이 구현은 아래의 A/B/C 전체 설계를 완성했다는 뜻이 아니다.

후속 구현 메모: 계획 **블록**에 현재 수동 상태(`pending/postponed/cancelled/external`)가 추가되었다. 실제 블록 연결은 완료로 표시한다. 이는 최신 상태만 저장하며 상태 변경 이력, 할 일 원본의 상태, 과거 회고 발행 스냅샷과 연결하지 않는다. 아래 분석에서 이 상태의 ‘사건·이유·시각’이 없다는 제한은 여전히 유효하다. 이 컬럼을 과거 발행일 당시의 상태라고 가정하거나 자동 피드백에 바로 사용하지 않는다.

### 현행 회고 검증 결과

후속 조치: 계획 없는 보고서는 `계획 없음`으로 표시하고, 여러 블록 중 특정할 수 없는 항목 단위 연결은 블록별 연결 판정에서 제외하며 `블록 미확인`으로 표시하도록 수정했다. 기존 스냅샷은 저장 내용을 수정하지 않고 조회 시 재판단한다. 아래 재현 결과는 수정 전 기준이다.

- 2026-10-31 격리 SQLite 프로브: 계획 0건·실제 1건(30분)에서 실제 시간은 30분으로 집계되지만 `planAchievementRate`는 0이다. `app/Views/pages/retrospect/report-content.php`는 이를 `계획 달성 0%`로 표시한다. 계획이 없으면 실패가 아니라 분모 없음으로 처리해야 새 피드백의 오해를 방지할 수 있다.
- 같은 프로브에서 한 계획 항목에 블록 2개와 블록 ID 없는 항목 단위 실제 1건(30분)을 만들었을 때 연결 실제 시간은 30분으로 한 번 집계되지만 두 블록 모두 연결된 것으로 계산되어 계획 연결률 100%가 나왔다. 블록을 식별할 수 없는 레거시 관계를 두 블록에 귀속해서는 안 된다. 실제 사용자 DB에 이 데이터가 존재하는지는 조사하지 않았다.
- 명시적 블록 연결 여러 건의 합계와 스냅샷 보존은 `tests/step0_baseline.php`가 확인한다. 계획 없는 날의 피드백 문장 생성, KPT 후속 의미 연결, 장기 변화와 새 규칙 엔진은 구현되어 있지 않으므로 실행 검증 대상이 아니다.
- 현재 회귀 테스트 `docker exec life_flow_app php /var/www/html/tests/step0_baseline.php`는 20/20 통과했다. 위 두 경계 사례는 임시 프로브로 실행했으며 애플리케이션 코드나 사용자 데이터를 변경하지 않았다.
- 현행 실행력 문구는 부담 미입력 시 잔량을 기준으로 `오늘 계획을 많이 실행했어요` 등의 판단을 반환할 수 있다(`ExecutionEnergyService::buildFeedbackMessage/milestoneFeedbackMessage`). 기본 −25의 단순 합이 계획 실행 자체를 증명하지 않으므로 새 회고 피드백의 사실 근거로 사용하면 안 된다.
- 이 결과는 격리된 시험 데이터와 코드 검토에 한정하며 실제 계정의 기록이나 사용자 경험, MySQL/MariaDB의 동일 사례는 검증하지 않았다.

## 1. 요약과 권고

하루흐름에는 일별 계획 블록, 실제 일정, 루틴 기록, 직접 작성한 KPT와 발행 당시 스냅샷이 이미 있다. 계획 없는 실제 일정과 여러 실제 일정을 연결한 계획을 지원한다. 다만 원문과 이후 행동의 의미 관계, 할 일의 미룸·취소·외부 처리, 과거 수정 이력은 저장하지 않는다. 기존 수치만으로 삶의 가치, 의도 달성, 성실성 또는 기록하지 않은 행동을 판정할 수 없다.

**권고: A 최소 변경형을 먼저 검증한다.** 발행 스냅샷을 이용해 출처가 분명한 사실 한두 개를 선택적으로 보여준다. 계획 없이 실제 기록만 있는 사용자에게도 동작한다. 별도 피드백 DB·AI·알림·강제 입력 없이 시작한다. 추후 사용자가 실제로 근거를 열어보고 도움이 된다고 판단했을 때만 명시적 연결(B)과 의미 분석(C)을 별도로 검토한다. 점수·랭킹·목표치 미달 판정이나 실행력 잔량에 기반한 성격 평가는 만들지 않는다.

**핵심 답변**

1. 기존 데이터로는 특정 기간의 기록된 실제 일정 수·시간, 연결이 명확한 계획 블록과 실제의 차이, 연결된 A/B 중요도별 실제 시간, 같은 루틴의 확인된 완료 횟수, 발행 당시 저장된 KPT와 스냅샷을 제시할 수 있다. 반복 활동의 동일성은 안정된 ID가 있을 때만 보장된다.
2. 특정 Try를 실천했는지, 서로 다른 제목의 기록이 같은 활동인지, 기록되지 않은 행동, 과거에 어떤 값으로 계획했는지, 미룸·취소·외부 처리의 이유나 실제 시각은 현재 데이터만으로 확정할 수 없다. 명시적 연결·상태 사건·버전 기록 등 추가 구조가 필요하다.
3. 첫 피드백으로는 사용자가 작성한 당시 날짜와 원문을 우선하며, 해당 발행일의 실제 기록 또는 확인 가능한 계획–실제 관계 한 가지를 출처와 함께 보여주는 것이 유용할 가능성이 높다. 효용은 사용자 시험으로 확인해야 한다.
4. 최근 발행 회고를 보여줄지 묻는 기존 안내, 신문형 원문·날짜·50:50/단일 시간표, 비연속 60회, 계획 없는 실제, 오래된 미완료 항목을 되살리지 않는 흐름을 보존한다.

## 2. 실제 구현 현황과 확인 수준

**확인됨**은 코드·스키마를 읽은 결과다. **추정**은 설계적 예측이며 배포 상태나 실제 사용자 통계는 아니다. **미확인**은 추가 검증이 필요하다.

| 영역 | 확인된 현행과 근거 | 피드백에서의 한계 |
|---|---|---|
| 기술·운영 | PHP MVC, Vanilla JS, MariaDB/MySQL과 SQLite fallback. 로컬 `docker-compose.yml`은 Apache app과 MariaDB 10.11, bind mount와 DB volume을 정의한다. `app/Core/Database.php`, `public/index.php` 참조. | 확인한 compose에는 분석 전용 큐·worker·스케줄러가 없다. 별도 운영 환경의 구성과 데이터 규모는 **미확인**. |
| 인증·격리 | `/retrospect`, `/calendar`, `/todo`, `/routine` 라우트는 auth 미들웨어를 사용하며 리포지터리 쿼리는 주로 `user_id`로 필터한다. POST는 CSRF, 출력은 `e()`를 사용한다. `public/index.php`, `app/Controllers/RetrospectController.php`, `app/Models/RetrospectRepository.php`. | 스냅샷 자식 조회의 일부는 `report_id`만 받는다. 소유한 상위 리포트를 먼저 확인해야 한다. 전체 엔드포인트의 권한 감사는 **미확인**. |
| 할 일 | `app/Services/TodoService.php::getDateData/complete`는 날짜별 `daily_plan_items`를 읽고 연결된 실제 일정이 있으면 완료로 표시한다. 미시간 항목은 실제 시간 선택 후 완료한다. | 연기·취소·외부 처리 상태/사건은 확인되지 않는다. 링크 존재는 기록 관계이지 행위의 의미나 완수 증명이 아니다. |
| 중요도 | `app/Views/pages/todo/index.php`는 A 중요·긴급, B 중요·비긴급, C 긴급·비중요, D 일반. 블록별 `importance_snapshot`이 있다. | 실제와 명확히 연결된 블록의 중요도만 해당 실제 시간에 귀속 가능. 기본 D가 사용자의 명시적 선택인지는 식별 불가. |

## 5. 수집·정규화·집계

분석 전용 수집 이벤트를 새로 만들지 않는다. MVP는 기존 발행 트랜잭션이 성공한 뒤 자식 스냅샷을 읽는다. B의 현재 데이터 분석은 계획/실제 생성·이동·수정·삭제, 루틴 상태 수정/삭제, 메모 수정/삭제, KPT 재발행 및 사용자 timezone 변경을 무효화 후보로 취급한다. 현재 `updated_at`만으로 누락 없는 변경 감지나 수정 전 값 복원이 된다고 가정하지 않는다.

* 기간은 사용자 timezone의 **로컬 날짜 [시작, 종료)**. 원천의 활동 날짜와 `submitted_at`/`created_at`을 별도로 표시하고, KPT 이후 기간은 대상일의 다음 날짜부터 비교하되 늦은 발행은 ‘실제로 적은 뒤’라고 단정하지 않는다. 이후 관계의 기준 시각은 명시적으로 선택해야 한다.
* 실제 총 시간 = `Σ(end_index-start_index)×10`분, **고유 event ID마다 한 번**, timed·삭제되지 않은 행만. 실제 시간이 미정이면 0이 아닌 미상으로 분리. 겹침 자료가 있으면 합산 시간과 겹침 제거 시간은 다르다. MVP는 단순 합계임을 밝히고 겹침 감지 시 시간 중복 제거가 필요한 해석은 생략한다. 현행 생성에서 겹침 검사 여부는 각 경로별로 확인해야 한다.
* 계획 B와 직접 연결된 실제 = `event.daily_plan_block_id=B.id`인 고유 실제들의 시간 합. 차이 = 실제 합 − `(B.end-B.start)×10`. 연결 없음은 실제 0분/실패가 아니라 ‘연결된 기록 없음’. 여러 실제는 모두 합하되 단일 실제를 여러 블록에 중복 배정하지 않는다. item-only 레거시는 블록 후보가 하나일 때만 별도 ‘항목 연결’로 제시하고, 둘 이상이면 블록별 비교 생략. 계획 이동/수정 전 상태는 모르므로 현재값과 발행 스냅샷을 섞지 않는다.
* 중요 A/B 투자 시간 = 해당 중요도 스냅샷을 가진 블록에 **직접 연결된** 고유 실제의 시간 합. B만 표시하려면 B 명시. 미연결 실제는 ‘중요하지 않음’이 아닌 **분류할 수 없음**으로 별도 표기. 예: “B로 표시한 계획과 연결된 실제 기록 90분”. 기본 D도 명시 선택으로 간주하지 않는다.
* 반복 = 같은 루틴 ID의 O 로그에서 `COUNT(DISTINCT log_date)` 또는 같은 안정된 사용자가 확인한 활동 ID의 실제 ID 수. 같은 제목 문자열, 복사된 템플릿, 삭제 후 재생성은 동일 활동이라고 확정하지 않는다. 루틴 완료와 일정 기록은 다른 단위이며 더하지 않는다. 예정 기회는 등록기간과 조회기간의 교집합의 로컬 날짜 수이나, 수정된 기간·중단/삭제 이력을 복원할 수 없으므로 과거 분모는 현재 저장값 기준임을 표시하고 불확실하면 생략한다.
* 기존 완료는 연결된 실제 존재라는 현재 UI 규칙에 한정한다. 미룸·취소·외부 처리의 건수는 **미지원**. KPT의 후속 행동도 실제 명시 연결이 생기기 전까지 표현하지 않는다. 활동의 여러 계획 연결은 현행 스키마 밖이며 가상 데이터만으로 집계하지 않는다.
* 현행 한 일정은 같은 날짜 `0 ≤ start < end ≤ 144`여서 자정 관통 한 행을 표현할 수 없다. 날짜를 나눈 별도 행은 각 활동일에 포함하고 자동 합병하지 않는다. 예상 밖 데이터는 제외·관측한다. DST 일자에 인덱스를 실제 경과 시간으로 단정하지 않는다. 사용자 timezone 변경 전후 로그의 과거 타임존은 추정하지 않는다.
* 변화 비교는 예컨대 직전 7일과 그 이전 7일을 같은 길이로 비교하되, 양 기간 각각 기록일 3일 이상 같은 대상·정의가 존재할 때만 ‘기록된 수’ 비교. 공백은 미기록이며 활동 부재가 아니다. 몇 달 공백이면 기준 미충족으로 비교를 생략한다. 모든 숫자는 `recorded`, `unknown`, `ambiguous`를 구분한다.

인덱스: `calendar_days(user_id,calendar_date)` 유일, `calendar_events(user_id,calendar_day_id,deleted_at)`, `daily_plan_blocks(daily_plan_item_id,sort_order)`, `routine_logs(user_id,log_date)` 및 `(routine_id,log_date)` 유일, `retrospect_reports(user_id,report_date)` 유일은 `sql/schema.sqlite.sql`/MySQL 대응 확인. 기간 쿼리는 날짜 범위와 사용자 조건을 함께 사용하고 실제 양 DB `EXPLAIN` 및 실측 후 추가 인덱스를 제안한다. 데이터량·실행계획은 미확인이다.

## 6. 피드백 후보와 규칙

MVP 후보는 저장하지 않는 응답 내부 객체: `{rule_id, version, report_id, period:{start,end_exclusive,tz}, as_of, facts, evidence:[{kind, snapshot_id}], confidence:'confirmed', text_key, args, fingerprint}`. `fingerprint=hash(user_id,rule_id,version,report_id,period,사실·근거의 정렬된 해시)`는 서버 내부 값; 원문·개인정보는 로그나 URL에 넣지 않는다. 규칙 생성과 화면 선택을 분리한다.

| ID / 목적 | 입력·발생 조건·최소 데이터·기간 | 값 / 신뢰 / 표현·금지 해석 | 근거와 중복 |
|---|---|---|---|
| D01 실제 기록 | 발행 스냅샷의 timed 실제 ≥1건, 해당 발행일 | 건수 및 중복 없는 ID별 기록 합, 확인됨. “이날 실제 일정 2건을 기록했어요.” 실제 삶 전체/충실도 아님 | 보고서 Actual snapshot ID, 같은 report/version/facts는 다시 새 발견으로 알리지 않음 |
| D02 의도–실제 | 직접 block FK가 유일하게 식별되는 계획 ≥1·실제 ≥1, 발행일 | 계획/연결 실제 시간 각각 및 차, 확인됨. “계획 60분에 연결된 실제 기록은 40분이에요.” 실패·남은 20분 미수행 단정 금지 | plan+actual snapshots, block ID 보존 검증; item-only 다중 후보 제외 |
| D03 중요 투자 | A/B 직접 블록 연결 실제 ≥1건, 발행일 | A/B별 기록 시간, 확인됨. “B로 표시한 계획과 연결된 실제 기록은 40분이에요.” 미연결 기록을 비중요로 분류 금지 | 블록 중요도 스냅샷·실제 스냅샷, 고유 actual ID |
| D04 루틴 이정표 | 동일 routine ID의 O 로그 60개, 대상일까지, 60 미만→60 이상 최초 확인 가능한 경우 | “누적 60일을 기록했어요. 꾸준히 이어온 시간을 돌아보세요.” 자동 습관 형성 단정 금지 | `routine_logs` 날짜·ID, 수정·삭제 시 재계산; 표시/재알림 기록이 없으면 새 알림 금지 |
| D05 기간 비교, 후속 | 동일 routine ID 또는 사용자 확인 활동, 각 7일 ≥3 기록일 | 기록된 횟수 차, 확인됨. “기록한 날짜가 2일에서 4일로 늘었어요.” 원인/삶의 변화 단정 금지 | 양 기간 원본 ID와 시간대; 같은 기간·사실 해시 억제 |
| C01 Try 연결, 후속 | 사용자가 구체적 Try와 실제를 직접 연결한 경우 ≥1 | “연결한 기록 2건이 있어요.” ‘시도 성공’이나 인과 단정 금지 | 확인 링크 ID, 대상 소유권·내용 버전; 연결마다 1회 |
| C02 유사 문장·키워드 | 선택적 탐색 후보만, 미확인 | 사용자 확인 전 노출·행동 성공 자동 판단 금지. Problem 반복의 의미 분석도 동일 | 후보·원문 외부전송 금지, 확인 전 신뢰 미확인 |

D01–D03은 이미 발행일 화면의 숫자와 중복될 수 있으므로 별도 문구가 새로운 맥락을 주지 않으면 생략한다. D04·D05는 발행 스냅샷에 필요한 과거 로그가 완전한지 먼저 검사한다. MVP는 강한 분석 예측을 하지 않고 항상 `confirmed` 사실만 노출한다. 상대 중요도에 따른 **선택 정책**은 후보에서 근거·시점·사용자 소유 검증 → 관련 직접 연결 우선 → 반복 문구·동일 수치 제거 → 최대 1개; 근거 없으면 0개. 매번 질문을 붙이지 않고 선택적으로만 제공한다. 관련 데이터 없는 계획 없는 날도 D01이 독립 동작한다.

**저장과 중복:** 현재 발행 스냅샷을 다시 여는 것과 새 알림은 다르다. MVP는 정적 사실을 회고 안에서 다시 보여줄 수 있지만 열람 상태·숨김·알림을 지원하지 않는다. 무상태만으로 ‘기기 간 재노출 금지’를 보장한다고 주장하지 않는다. 필요성이 입증되면 `feedback_impressions(user_id, fingerprint UNIQUE, first_seen_at, hidden_at NULL, rule_version)` 등 별도 제약과 보존·삭제 정책을 설계한다. 분석에 재현 가능한 ‘당시 피드백’을 영구 보존하려면 발행 트랜잭션에 버전/근거 스냅샷 추가가 필요하며, 현재 스키마의 재발행 덮어쓰기와 충돌한다. 승인 전 MVP에서는 신설 저장/과거 결과 재현을 약속하지 않는다.

## 7. KPT와 후속 행동 연결

| 방법 | 정확도와 비용 | 결론 |
|---|---|---|
| 제목 키워드 | 동음이의어·부정문·시간 표현에 취약. 오탐 높음, 구현은 낮음 | 명시적 사실이나 성공 문구에 사용 금지. |
| 기존 태그·목표 | 활동 분류는 보조하나 KPT와의 FK 없음. 동일 태그 ≠ 동일 의도 | Try 연결로 주장 금지. |
| 선택적 사용자 명시 연결 | 의도 확인 가능하나 선택 부담·관계 삭제/본문 변경 처리 필요 | B 후보. 확인된 ‘관련’만 표시, 필수 입력 금지. |
| AI 의미 분석 | 요약·의미 후보 가능하지만 원문 전송·오탐·비용·재현성 문제 | C 연구 후보, 기본 경로에 두지 않음. |

KPT는 항상 원문 그대로 유지한다. `confirmed`는 사용자의 명시 연결 또는 FK에 근거한 기록 관계, `possible`은 확인 전 후보, `none`은 근거 없음으로 분리한다. ‘확인됨’은 실천의 질이나 인과까지 확인한 뜻이 아니다. 장기 비교는 동일한 식별자와 동일 기간 정의가 있을 때만 기록된 수치를 비교한다. 과거 회고에서 당시 스냅샷과 후속 새 계산은 `발행 당시`/`이후 기록 (분석 기준일)`로 분리하며, 당시 피드백 영구 보존은 현행 구현으로 불가능하다.

신문형 날짜 시각 위계, 일정의 두 시간표와 집중 비율, KPT 10분 작성 경험을 바꾸지 않는다. 시각·접근성·실제 사용성은 구현 후 작은 화면과 데스크톱에서 확인해야 한다.

## 9. API와 처리 순서

MVP는 기존 `POST /retrospect/publish`와 `GET /retrospect/report?date=...`, `GET /retrospect/report/preview?date=...`를 재사용한다. 기존 응답 계약을 깨지 않고 발행 성공 후 report 조회 시 선택적 섹션을 렌더링하는 편이 간단하다. 일정 접속의 `getDayViewData`는 이미 최신 보고서 미리보기를 조립하므로 긴 기간 분석을 여기에 추가하지 않는다. 필요 시 미리보기 열기 이후 별도 요청으로 지연시킨다.

후속 예시 `GET /retrospect/feedback?date=YYYY-MM-DD` → `{ok:true, report_date, basis:'published_snapshot', as_of, items:[{rule_id,text,evidence:[{type,date,label}]}]}`. 날짜 유효성·auth·소유권을 서버에서 검증하고 원문, 내부 쿼리 및 다른 사용자 ID를 반환하지 않는다. 실패 시 보고서 원문/일정은 정상 사용하고 피드백만 생략한다. 클라이언트 타임아웃·취소/재요청은 읽기 전용으로 안전하게 처리한다. 새 API는 실제로 지연 로딩이 필요한 경우에만 추가한다.

`POST /retrospect/try-links` 등 사용자 확인 기능은 B 이후 별도 계약·CSRF·소유권·동시성·삭제/재발행 정책을 설계한다. 사용자 쓰기 API는 서버 생성 idempotency key와 유일 제약을 사용하며 중복 제출은 기존 결과를 돌려준다. 모델 외 SQL·뷰 내 비즈니스 로직 금지, 서비스가 후보 계산을 담당한다.

## 10. 성능·보안·운영

MVP는 발행 스냅샷에서 O(n) 일별 집계, 느린 장기 쿼리·백그라운드 작업·새 캐시 없음. 후보 생성 시간과 DB 쿼리 수를 계측해 기존 p95 보고서/일정 로딩과 비교한다. 목표 예: 기존 대비 유의미한 회귀가 없을 것(수치 기준은 실측 후 확정). 실패는 원문 렌더링과 독립. 재발행은 스냅샷을 대체하므로 그 다음 요청에서 새 사실을 계산한다.

장기 집계가 실제 병목이 되면 사용자·기간·timezone·규칙버전·데이터 기준시각이 포함된 캐시를 도입한다. 생성/수정/삭제/루틴 정정/태그 및 중요도 변경/재발행/시간대 변경을 트랜잭션 이후 무효화하고, 누락 감지를 위한 TTL과 read-through 재계산을 둔다. cross-day 변경 시 이전·새 기간 모두 무효화한다. 현재 `updated_at`만으로 완전한 무효화가 보장되는지 미확인; 검증 전 캐시를 영구화하지 않는다. 선계산 작업과 큐/운영자 재처리 역시 운영 인프라 검증 후 도입한다.

계정 범위는 모든 원천과 조인에 적용하고, report ID를 직접 받아도 부모 소유권부터 확인한다. 응답 텍스트 이스케이프, prepared statement, 기록이 포함된 로그 금지, 인증과 POST CSRF를 유지한다. AI를 나중에 고려해도 명시적 동의, 최소 전송, 저장·보존·삭제·제3자 계약·한국어 정확도·비용 상한 및 실패 시 규칙 기반 대체가 선행되어야 한다. 산출물과 원문이 자동 수정되는 경로는 두지 않는다. 현재 트리에서 AI 서비스·비용 추정 근거는 확인되지 않았으므로 숫자를 임의로 제시하지 않는다.

## 11. 테스트 설계

모든 사례에서 사용자 A/B 데이터와 동일 날짜를 분리하고, 각 결과의 근거 ID·기간·단위를 함께 확인한다. 아래는 **미구현 설계 테스트**이며 실제로 이미 실행된 결과가 아니다.

| 입력 | 기대 결과 / 노출 가능한 문구 |
|---|---|
| 계획 0, 실제 timed 2건(30·40분) | D01 2건/70분. “실제 일정 2건을 기록했어요.” 계획 실패 문구 없음. |
| 60분 계획 B 1개, 직접 연결 실제 40분 1개 | D02 −20분, D03 40분. “계획 60분에 연결된 실제 기록은 40분이에요.” |
| 60분 계획 2개, 한 블록에 실제 20·10분 | 해당 블록 실제 30분, 다른 블록 미연결. 부분 수행이라고 판정하지 않음. |
| B 계획에 직접 연결된 실제 3건, 총 90분 | “B로 표시한 계획에 연결된 실제 기록은 3건, 90분이에요.” |
| 동일 루틴 O 60일, 날짜 불연속 | 60회, “누적 60일을 기록했어요.” 연속 요구·자동성 단정 없음. |
| 명시적 Try→실제 2건, 사용자 확인 링크 | B 단계 C01만 “연결한 실제 기록 2건”. ‘성공’은 아님. |
| Try ‘오전 공부’, 제목 유사 실제만 | 명시 연결 없음. 실천 성공·연결 문구 미표시. |
| KPT 수개월 없음 / 몇 달 만의 복귀 | 기록 부재를 실패로 표시하지 않음. 최소 근거 부족이면 후보 0. 원하면 지난 발행 회고를 기존 경로에서 볼 수 있음. |
| 기록 0 또는 비교 기간 중 한쪽 기록일 2일 | 후보 0 또는 당일 확인 사실만. 비교·성격 판단 없음. |
| 발행 후 원본 삭제/수정 | 기존 발행 스냅샷은 그대로; 재발행 후 변경. 현재 분석은 현재 자료로 별도 표시. |
| 같은 요청 재실행 | 같은 원천·규칙은 동일 fingerprint/문구. 열람 중복 억제는 저장 기능 없는 MVP에서 보장하지 않음. |
| 같은 실제를 plan join과 routine 체크에서 함께 조회 | 고유 actual ID 1건, routine은 별도 1회; 시간 이중 합산 금지. |
| A/B 사용자에 같은 날짜·유사 제목 | A 응답에 B 원문·ID·수치 0건; 타인 report_id 직접 요청 거부. |
| 레거시 item ID만 있고 동일 item 블록 2개 | 블록별 실제 귀속 불가, 차이 문구 생략. |
| 겹친 실제 60분 두 개 / 자정 split | 120분 기록 합과 중복 제거 시간 구분; split은 각각의 날짜로만 합산. |
| 시간대 변경·늦게 작성·재발행 | 대상일과 작성/발행 시각을 혼동하지 않음; 이전 timezone 불명 시 단정 금지. |

구현 시 SQLite와 MySQL/MariaDB 각각에서 경계일·유저 격리·트랜잭션·NULL·재발행을 실행한다. 성능은 대량 데이터 EXPLAIN 및 실제 UX에서 360/390/430px, 키보드·스크린리더, 기존 확인창 거절, 느린 네트워크와 오류를 테스트한다. 사용성은 “이 문장이 어떤 행동을 돕는지, 근거를 이해했는지, 부담스럽지는 않았는지”를 인터뷰하고, 긍정 클릭만으로 효용을 추정하지 않는다.

## 13. 대안 비교·결정 사항

* **A 최소 변경형:** 낮은 운영 부담과 재현 가능한 사실이 장점. 장기 개인화·의도 연결은 제한적. 기본 추천.
* **B 데이터 연계 강화형:** 명시적 관계의 가치는 크지만 링크·스냅샷 버전·상태 전이와 소유권의 비용이 높다. 사용자 선택과 데이터 정합성 설계가 선행될 때만 착수.
* **C AI/NLP:** 표현이 다양한 텍스트의 탐색 후보에는 잠재 가치가 있지만, 근거 없는 심리·성격 판단과 민감 원문 전송의 위험이 크고 동일 결과 재현이 어렵다. 기본 기능이나 초기 필수 조건으로 추천하지 않는다.

구현 전 결정: (1) 무엇을 ‘도움이 된 피드백’으로 판단할지와 사용성 평가 방법, (2) 선택형 근거 보기의 위치와 발행 직후 노출 여부, (3) 보고서 재발행 시 당시 분석 보존이 실제로 필요한지, (4) item-only 레거시 링크를 어떻게 표시할지, (5) 시간대 변경·과거 삭제 데이터의 기준, (6) Try 명시 연결을 사용자가 원할 때의 연결 단위와 수정·철회, (7) 60회 격려 문구의 표현, (8) 중복 노출 방지가 실제 제품 요구인지, (9) 실행력 표시의 별도 제품 결정. 이 문서는 실행력 시스템 삭제나 기본 점수 변경을 승인하지 않는다.
