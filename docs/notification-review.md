# 알림 기능 검토

검토일: 2026-11-10 (Asia/Seoul)

## 범위

디자인 통일 이후 남은 알림 검토다. `NotificationService`, Calendar 데이터 공급 경로, 루틴/목표 저장값, Android 브리지 필터와 기존 연동 문서를 확인했다. 최초 검토에서는 기능 코드를 변경하지 않았다. 이후 사용자 요청으로 계획 블록 알림과 선택 UI를 구현했다.

재현은 PHP의 별도 메모리 SQLite DB와 Node VM의 가짜 Android 브리지에서 수행했다. 기존 개발 DB·계정에는 접근하지 않았다. Android 네이티브 소스가 이 저장소에 없어 실제 수신·권한·재부팅 복원·예약 취소 완료 여부는 검증하지 않았다. 일반 Android Chrome에는 이 앱 전용 WebView 브리지가 없으므로 브리지 기반 알림 검수와 구분한다.

## 확인된 문제

### 해결됨 — P1. 배치한 계획 블록의 알림이 누락됨

후속 구현: 실제 블록의 알림 사용 여부와 사전 시간을 저장하고 일정/할 일 상세에서 함께 편집한다. 키는 날짜와 block ID를 사용한다. SQLite·MySQL 및 웹 저장/재열기/이동/삭제/전역 설정 연계를 검증했다. 미지원 스키마에서는 원본 시각으로 대체하지 않고 알림 편집을 비활성화한다. 아래는 수정 전 재현 기록이다.

`CalendarService::getDayViewData()`는 `planReminderItems`를 `daily_plan_items`에서 만든다. 실제 배치 시간은 `daily_plan_blocks`에 저장되지만 원본 할 일은 시간 미정으로 남는 것이 현재 데이터 모델이다. `NotificationService::calendarPlanPayload()`는 원본의 `startIndex`가 null이면 제외한다.

- 재현: 90일 뒤 날짜에 시간 미정 할 일 한 개를 만들고 10:00~11:00, 15:00~16:00 두 계획 블록을 배치한다.
- 결과: DB의 계획 블록은 2개, 원본 시작 시각은 null, 알림은 0개다.
- 추가 재현: 시간 있는 원본에 같은 두 블록을 구성하면 알림은 원본 시각의 1개만 만들어진다.
- 영향: 현재의 할 일→계획 배치 흐름에서 시작 전 알림이 누락되거나 실제 블록 시각과 달라진다.
- 위치: `app/Services/CalendarService.php`의 `getDayViewData()`와 `buildPlanReminderItems()`, `app/Services/NotificationService.php`의 `calendarPlanPayload()`.
- 수정 방향: 알림 전용 목록은 날짜별 실제 계획 블록에서 만들고 안정적인 block ID를 예약 키에 포함한다. 블록 미지원 스키마에서는 기존 원본 시간의 대체 경로를 유지한다. 같은 변환 함수를 사용하는 `planActivityItems`는 시간 미정 배치 원본도 보여야 하므로 함께 바꾸면 안 된다.

### P2. 목표 마감 알림의 시간대 오프셋 누락

목표의 `fireAt`은 `YYYY-MM-DDTHH:mm:ss`로 만들어져 오프셋이 없다. 바깥 payload의 `timeZone`과 별개로 브리지는 `Date.parse(item.fireAt)`으로 과거 여부를 판단한다. 이 해석은 사용자 시간대가 아니라 기기의 현지 시간에 의존한다.

- 재현: 사용자 시간대를 `America/New_York`, 기기 해석 시간대를 `Asia/Seoul`, 목표 알림을 2026-11-12 12:00으로 지정한다.
- 결과: 생성 문자열은 `2026-11-12T12:00:00`, 기대값은 `2026-11-12T12:00:00-05:00`이다. 웹에서 해석한 시점이 14시간 빠르다.
- 추가 재현: 기대 시각의 한 시간 전을 현재 시각으로 두면 정상 미래 알림인데도 브리지 필터에서 제거되어 네이티브로 넘어간 항목 수가 0개다.
- 영향: 마감일과 D-1 알림의 웹 측 과거 판정이 틀릴 수 있다. Android의 최종 예약 시각 자체는 네이티브 구현이 없어 단정하지 않는다.
- 위치: `app/Services/NotificationService.php`의 `goalDeadlinePayload()`, `public/assets/js/components/android-bridge.js`의 `Date.parse` 필터.
- 수정 방향: 사용자 `DateTimeZone`으로 마감일과 D-1의 시점을 만들고 `DATE_ATOM` 오프셋을 포함한다. 두 경로 모두 같은 과거 제외 정책을 적용한다.

### P2. 루틴별 저장 시각이 알림 데이터에 반영되지 않음

루틴 생성/수정은 `routines.reminder_time`을 저장하고 조회 모델도 반환한다. 하지만 `routineReminderPayload()`는 모든 항목의 `time`을 설정의 `routine_reminder_time`으로 채운다.

- 재현: 개별 루틴의 알림 시간을 16:45, 설정의 공통 루틴 시간을 14:00으로 둔다.
- 결과: DB 조회값은 16:45지만 전송되는 루틴 알림 시각은 14:00이다.
- 영향: 루틴 관리 화면에서 시각을 바꿔도 알림 데이터에 변화가 없다.
- 위치: `app/Models/RoutineRepository.php`의 생성/수정 및 `listNotificationEnabled()`, `app/Services/NotificationService.php`의 `routineReminderPayload()`.
- 수정 방향: 현재 개별 시각 입력 UI를 유지한다면 개별 값 우선, 누락/무효일 때만 공통 시각 대체가 일관적이다. 공통 시간만 쓰는 제품 규칙이라면 개별 시간 입력과 저장을 제거해야 하므로 규칙을 먼저 정리한다. 현재 연동 문서는 공통 시각을 설명해 UI와 불일치한다.

## 정상 확인과 미확정 항목

- 유효한 시작 시각을 직접 주입한 기존 계산 경로는 90일 뒤 알림 1개를 만들고 어제의 알림은 0개로 제외한다. 기존 미래 날짜 검사는 이 계산 경로만 확인하므로 실제 배치 블록 누락을 잡지 못한다.
- Calendar payload에는 날짜별 `operation: replace`, `scope: calendar_plan`, `scopeKey`가 있다. 실제 중복 방지는 네이티브가 안정적인 key와 범위별 교체 계약을 구현해야 보장된다.
- 루틴·목표의 부분 동기화에는 교체 범위가 명확하지 않다. 삭제/중단 후 기존 예약 제거와 다른 종류의 알림 보존 정책은 Android 구현과 함께 확인해야 한다. 웹 코드만으로 기존 예약이 반드시 남는다고 단정하지 않는다.
- 웹 로그아웃 경로에서 예약 취소 호출은 확인되지 않았다. 로그아웃·계정 전환 시 네이티브 예약을 정리하는 별도 정책이 있는지 Android 측 확인이 필요하다.
- 블록별 알림 선택은 후속 구현으로 완료했다. `notification-feature-implementation.md`에 현재 동작과 수동 검수 절차를 기록했다.
- 기존 문서의 Calendar 타임스탬프 `+09:00` 고정 설명은 구현과 다르다. Calendar는 사용자 시간대의 오프셋을 출력한다.

## 수정 우선순위와 재검증

1. 계획 블록 알림 데이터 공급 경로를 고친다. 시간 미정 원본·여러 블록·이동·크기 변경·삭제·원본 삭제 및 레거시 대체 경로를 검증한다.
2. 목표 알림의 마감일/D-1 오프셋과 사용자/기기 시간대 차이, 과거 제외, DST 경계를 검증한다.
3. 루틴별/공통 시각 우선순위를 정하고 저장→동기화 데이터까지 검사한다.
4. Android 측 범위별 교체·취소·로그아웃 정책을 확인한 뒤 실제 수신·중복·재부팅 복원을 검증한다.

수동 재현: 미래 날짜의 할 일 하나를 두 시간대에 배치한 뒤 동기화 데이터의 항목 수와 시각을 비교한다. 루틴별 시간과 공통 시간을 다르게 저장해 전송값을 확인한다. 서로 다른 사용자/기기 시간대에서 목표 마감과 D-1을 확인한다. 실제 수신 확인은 웹 재현과 별도다.

재현 스크립트와 결과 JSON은 로컬 `storage/notification-review/2026-11-10/`에 보관한다. 의도적으로 현재 문제를 드러내는 검수 스크립트이며 정상 회귀 테스트 모음에 추가하지 않았다.
